## Technical Notes

### Memory Profiling Tools

**Option 1: valgrind + massif** (most mature)

```bash
# Run with massif
valgrind --tool=massif --massif-out-file=massif.out ./target/release/powers

# Visualize
ms_print massif.out > massif.txt
```

**Option 2: heaptrack** (good visualization)

```bash
heaptrack ./target/release/powers
heaptrack_gui heaptrack.powers.*.gz
```

**Option 3: dhat** (Rust-friendly)

```rust
use dhat::{Dhat, DhatAlloc};

#[global_allocator]
static ALLOCATOR: DhatAlloc = DhatAlloc;

fn main() {
    let _dhat = Dhat::start_heap_profiling();
    // Your code here
}
```

### Integration with Criterion

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn memory_benchmark(c: &mut Criterion) {
    let mut group = c.benchmark_group("memory");

    group.bench_function("training_iteration", |b| {
        b.iter_custom(|iters| {
            let start_mem = get_memory_usage();
            let start = Instant::now();

            for _ in 0..iters {
                black_box(training_iteration());
            }

            let duration = start.elapsed();
            let end_mem = get_memory_usage();

            println!("Memory used: {} MB", (end_mem - start_mem) / 1_000_000);
            duration
        });
    });

    group.finish();
}
```

### Key Metrics to Measure

1. **Peak memory usage** (MB):

   - Forward pass
   - Backward pass
   - Full iteration
   - Full training session

2. **Memory per item**:

   - Bytes per cut
   - Bytes per state variable
   - Bytes per scenario

3. **Memory growth**:

   - Memory vs iteration count
   - Memory vs number of cuts
   - Memory vs problem size

4. **Allocation patterns**:
   - Number of allocations per iteration
   - Average allocation size
   - Allocation hot spots

### Expected Findings

Based on architecture review, likely findings:

- **Cut storage**: 56 bytes/cut (can be optimized)
- **Scenario storage**: Allocates per iteration (could pool)
- **Solver state**: May allocate unnecessarily
- **Graph traversal**: May clone unnecessarily

### Optimization Opportunities

High-priority candidates:

1. **Cut storage compaction**: Use smaller data types
2. **Scenario pooling**: Reuse scenario objects
3. **State update in-place**: Avoid clones
4. **Solver warm-start**: Reuse basis vectors

### Memory Usage Guidelines for Users

Document expected memory for typical problems:

- Small (5 stages, 100 scenarios): ~50 MB
- Medium (20 stages, 500 scenarios): ~500 MB
- Large (50 stages, 1000 scenarios): ~2 GB

Formula:

```
Memory (MB) ≈ num_stages × num_scenarios × state_size × 0.01
            + num_cuts × 0.000056
            + solver_overhead (100 MB)
```

## Notes for Implementer

### Getting Started

1. Research memory profiling tools for Rust
2. Choose tool appropriate for Linux/macOS
3. Run basic profiling on example problem
4. Look for obvious hotspots

### Quick Wins (if time permits)

Some easy memory optimizations:

- Replace `Vec<f64>` with `Vec<f32>` where precision allows
- Use `&str` instead of `String` where possible
- Pool scenario objects instead of allocating
- Use `Box<[T]>` instead of `Vec<T>` for fixed-size arrays

### Testing Locally

```bash
# Build release binary
cargo build --release

# Profile with valgrind
valgrind --tool=massif ./target/release/powers example/config.json
```
