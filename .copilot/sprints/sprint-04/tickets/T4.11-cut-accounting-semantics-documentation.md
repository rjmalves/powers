## Context

During T4.1 implementation (timing instrumentation), a question arose about "returning cuts" statistics that led to investigation and important semantic clarifications. The user noticed that the number of returning cuts reported was sometimes larger than the number of active cuts, which seemed like a potential bug.

**Investigation revealed this is CORRECT BEHAVIOR**, not a bug, and represents important SDDP algorithm semantics that need documentation.

---

## Discovery Summary

### The Question

```
Iteration 5: +44 new, -28 dominated, +33 returned, 73 active
```

User asked: "Why can we have 33 returning cuts when we only have 73 active cuts total? This seems wrong!"

### The Answer

**"Returning cuts" are counted PER-STAGE across the iteration**, not per-node at the end:

1. **Each stage has its own FCF** with its own cut pool and cut IDs
2. **Returning cuts = reactivation ATTEMPTS**, not guarantees
3. **Some returning cuts are immediately dominated again** by newer cuts in the same batch
4. **The accounting equation doesn't hold**: `old_active + new - removed + returned ≠ new_active`
5. **This is BY DESIGN**: The algorithm explores states that reactivate old cuts, but those cuts may be superseded by better cuts before becoming truly active

### Key Semantic Insights

1. **Cut IDs are per-node, not global**: Stage 1's cut ID 5 is different from Stage 3's cut ID 5
2. **Returning cuts are aggregated across stages**: 33 cuts returned = sum across all 11 stages
3. **Active cuts are counted graph-wide at end**: 73 active = sum across all stages AFTER all operations
4. **Intra-batch domination**: A cut marked for "return" can be dominated again before the batch completes
5. **Diagnostic statistics**: These numbers provide insight into algorithm dynamics, not strict accounting

## What Was Documented

### Code Investigation

- **src/fcf.rs**: `update_old_cuts_domination()` marks cuts for return but doesn't set `.active = true`
- **src/fcf.rs**: `add_cuts_batch()` Phase 2 finds dominated cuts with `count == 0 && active`
- **src/sddp/mod.rs**: Returning cuts are accumulated: `backward_cuts_returned += batch_result.returning_cut_ids.len()`
- **Behavior verified with POWERS_CUT_DEBUG=1**: Returning cuts can have `.active=false` and be immediately dominated

### Debug Output Analysis

```
[FCF]      Returning cuts so far: {0}
[FCF] --- PHASE 2: Finding dominated cuts ---
[FCF]   Cut 0: active=false, count=0, rhs=1264.89 💤 ALREADY INACTIVE
```

Cut 0 was marked for return (incremented its `non_dominated_state_count`), but:

- It's still `active=false` (won't be caught by domination filter)
- Later cuts in the batch dominated it again
- It never actually becomes active

## Technical Notes

### Cut Lifecycle

```
INACTIVE → [dominates new state] → MARKED FOR RETURN → [dominated by newer cut] → STILL INACTIVE
                                  → [not dominated]   → ACTIVE
```

### Accounting Non-Identity

The equation `old_active + new - removed + returned = new_active` does NOT hold because:

1. **Temporal overlap**: Returning and removing can affect the same cuts
2. **Intra-batch domination**: A cut can be marked for return but dominated before batch completes
3. **Stage aggregation**: Operations are accumulated across stages with independent cut pools

### Correct Interpretation

| Statistic       | Meaning                                                         |
| --------------- | --------------------------------------------------------------- |
| `+44 new`       | 44 new cuts added across all stages                             |
| `-28 dominated` | 28 cuts removed due to dominance across all stages              |
| `+33 returned`  | 33 reactivation ATTEMPTS across all stages                      |
| `73 active`     | Actual number of active cuts across all stages at iteration end |

**Gap = 73 ≠ (old + 44 - 28 + 33)** is EXPECTED due to intra-batch dynamics.

## Notes for Future Reference

### When Users Ask About Cut Statistics

**Key Points to Communicate**:

1. Statistics are **diagnostic**, not strict accounting
2. "Returning cuts" are **reactivation attempts**, not guarantees
3. Intra-batch domination is **by design** (newer cuts supersede older)
4. The final "active cuts" count is the **ground truth**
5. Gap between expected and actual is **normal and correct**

### Design Rationale

The batch cut selection algorithm optimizes for:

- **Correctness**: All cuts see consistent pool state
- **Performance**: Batch processing is 154× faster
- **Determinism**: Index-ordered processing ensures reproducibility

The "returning cuts" statistic provides insight into algorithm dynamics:

- High count = exploring states far from previously visited
- Low count = converging to known region
- Immediate re-domination = rapid policy improvement
