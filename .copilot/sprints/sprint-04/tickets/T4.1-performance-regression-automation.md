## Context

Sprint 3 delivered a **154× speedup** in cut selection through batch optimization. As the codebase evolves and new optimizations are added, we need automated performance regression detection to ensure we don't silently regress this performance.

**Critical Gap Identified**: The algorithm currently lacks internal timing instrumentation. `IterationResult` has only `iteration_time: Duration` with no breakdown of where time is spent (solver, cut selection, forward/backward passes). This makes it impossible to diagnose WHERE performance regressions occur.

**Why This Is Critical**:

- Batch cut selection changed hot path (baseline protection needed)
- Future optimizations need comparison data
- Industry standard for HPC software
- Blocks production deployment without performance monitoring
- **NEW**: Without timing breakdown, we can't diagnose performance issues or validate optimizations

**Current State**:

- Manual benchmarking only (benches/ directory with 18 benchmarks across 4 files)
- No CI integration
- No documented baseline metrics
- No regression detection
- **No internal timing instrumentation** (critical gap)

**Target State**:

- Automated Criterion benchmarks for critical operations
- CI integration with regression detection
- Documented performance baselines with hardware specs
- Regression threshold enforcement (>5% slowdown fails CI)
- **Internal timing breakdown** in IterationResult (ForwardPassTiming, BackwardPassTiming)

## Technical Notes

### Benchmark Structure

Use Criterion best practices:

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion, BenchmarkId};

fn forward_pass_benchmark(c: &mut Criterion) {
    let (mut sddp, saa) = create_benchmark_problem();

    c.bench_function("forward_pass_single_scenario", |b| {
        b.iter(|| {
            // Use black_box to prevent compiler optimization
            black_box(sddp.forward_pass(black_box(&saa.scenarios[0])))
        });
    });
}

criterion_group!(benches, forward_pass_benchmark);
criterion_main!(benches);
```

### Critical Operations to Benchmark

1. **Solver calls** (60-80% of runtime):

   - Subproblem construction
   - LP solve with warm-start
   - Basis extraction

2. **Cut selection** (<0.5% of runtime, but recently optimized):

   - Batch cut addition (10, 100, 1000 cuts)
   - Dominance checking
   - Cut activation/deactivation

3. **SDDP operations** (10-20% of runtime):

   - Forward pass (single scenario)
   - Backward pass (single stage)
   - Full iteration (forward + backward)

4. **Data structures** (<5% of runtime, but frequently accessed):
   - State updates
   - Cut evaluation
   - Scenario sampling

### CI Configuration Tips

```yaml
# .github/workflows/benchmarks.yml
name: Performance Benchmarks

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  benchmark:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions-rs/toolchain@v1
      - name: Run benchmarks
        run: cargo bench --bench '*' -- --save-baseline pr
      - name: Compare to main
        run: |
          git fetch origin main
          git checkout origin/main
          cargo bench --bench '*' -- --save-baseline main
          # Use criterion-compare or custom script
          cargo bench --bench '*' -- --baseline main --baseline pr
      - name: Upload results
        uses: actions/upload-artifact@v3
        with:
          name: benchmark-results
          path: target/criterion/
```

### Regression Threshold

- **5% slowdown**: Investigate and document if intentional
- **10% slowdown**: Block merge unless justified
- **20%+ slowdown**: Critical regression, must fix

```bash
cargo bench -- --baseline before

```

### Common Pitfalls

- **Don't forget `black_box`**: Prevents compiler from optimizing away benchmark code
- **Use realistic problem sizes**: Too small = unrealistic, too large = slow benchmarks
- **Warm up the benchmark**: Criterion does this automatically, but be aware
- **Watch for variance**: High variance indicates unstable benchmark
