## Context

Currently, the `train()` function in `sddp.rs` returns `Result<(), String>`, providing no information about the training process. This makes it impossible to:

- Validate convergence in tests
- Assert that algorithm reached expected bounds
- Check stability of convergence
- Debug convergence issues
- Provide users with training insights

Integration tests need to verify numerical accuracy and convergence behavior, but without access to convergence history, they can only check that training completes without errors.

**Sprint 1 Gap**: Integration tests mentioned needing convergence validation but couldn't implement it.

## Technical Notes

### Struct Design

```rust
use serde::{Deserialize, Serialize};
use std::time::Duration;

/// Result of a single SDDP training iteration
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct IterationResult {
    /// Iteration number (1-indexed)
    pub iteration: usize,

    /// Lower bound from backward pass (approximation of optimal value)
    pub lower_bound: f64,

    /// Average cost across all forward passes (upper bound estimate)
    pub upper_bound: f64,

    /// Individual forward pass costs
    pub forward_costs: Vec<f64>,

    /// Absolute gap between upper and lower bound
    pub gap: f64,

    /// Relative gap (gap / lower_bound if lower_bound != 0)
    pub relative_gap: f64,

    /// Time taken for this iteration
    pub iteration_time: Duration,
}

/// Result of SDDP training containing convergence history and final statistics
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TrainingResult {
    /// Iteration-by-iteration results
    iterations: Vec<IterationResult>,

    /// Final lower bound (from last iteration)
    final_lower_bound: f64,

    /// Final upper bound (from last iteration)
    final_upper_bound: f64,

    /// Best (lowest) upper bound seen during training
    best_upper_bound: f64,

    /// Iteration where best upper bound was achieved
    best_iteration: usize,

    /// Total training time
    total_time: Duration,

    /// Number of cuts in final policy
    num_cuts: usize,

    /// Why training stopped
    termination_reason: TerminationReason,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum TerminationReason {
    /// Completed all requested iterations
    IterationLimit,
    /// Reached convergence tolerance (future)
    Converged { gap_tolerance: f64 },
    /// Time limit reached (future)
    TimeLimit,
}
```

### Helper Methods

```rust
impl TrainingResult {
    /// Get the final absolute gap
    pub fn final_gap(&self) -> f64 {
        self.final_upper_bound - self.final_lower_bound
    }

    /// Get the final relative gap (gap / lower_bound)
    pub fn relative_gap(&self) -> f64 {
        if self.final_lower_bound.abs() < 1e-10 {
            f64::INFINITY
        } else {
            self.final_gap() / self.final_lower_bound.abs()
        }
    }

    /// Check if algorithm converged within tolerance
    pub fn converged(&self, gap_tolerance: f64) -> bool {
        self.final_gap().abs() <= gap_tolerance
    }

    /// Get all lower bounds
    pub fn lower_bounds(&self) -> Vec<f64> {
        self.iterations.iter().map(|it| it.lower_bound).collect()
    }

    /// Get all upper bounds
    pub fn upper_bounds(&self) -> Vec<f64> {
        self.iterations.iter().map(|it| it.upper_bound).collect()
    }

    /// Access iteration results
    pub fn iterations(&self) -> &[IterationResult] {
        &self.iterations
    }
}
```

### Performance Considerations

- **No overhead during training**: Only store data that's already computed
- **Minimal allocation**: Use `Vec::with_capacity` for iterations
- **No cloning**: Store computed values directly
- **Gap calculation**: Compute once per iteration, not in helper methods

- **No breaking changes yet**: This ticket only creates the struct

## Notes for Reviewer

**Critical Design Decisions**:

1. **Separate IterationResult**: Makes history queryable and analyzable
2. **Store all forward costs**: Enables variance analysis (future)
3. **Serializable**: Future-proofs for checkpointing
4. **Helper methods**: Convenience without performance cost

**Questions to Consider**:

1. Should we store standard deviation of forward costs?
2. Do we need wall-clock time vs CPU time?
3. Should gaps be computed lazily or stored?

**Review Focus**:

- API ergonomics for tests and users
- Documentation clarity
- Performance implications (should be none)
