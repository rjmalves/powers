## Context

T3.7 implemented **Phase 1** of input validation (minimal config validation), deliberately deferring comprehensive validation to allow the Factory API to ship quickly. The `input.rs` file contains explicit TODO comments outlining the remaining validation work:

```rust
// TODO (T3.7 expansion): Add comprehensive validation methods
//

// pub fn validate_graph(graph: &GraphInput) -> Result<(), PowersError>
// pub fn validate_recourse(recourse: &Recourse, system: &SystemInput) -> Result<(), PowersError>
// pub fn validate_consistency(...) -> Result<(), PowersError>
```

### Current State

**Validation Coverage**:

- ✅ **Config**: num_iterations, num_forward_passes, num_simulation_scenarios > 0
- ❌ **System**: No validation (panics on invalid data during `build_sddp_system()`)
- ❌ **Graph**: No validation (panics on invalid data during `build_sddp_graph()`)
- ❌ **Recourse**: No validation (silent failures or runtime errors possible)
- ❌ **Cross-file consistency**: No validation

**Error Handling**: T3.9 provided comprehensive `PowersError` hierarchy with:

- `ValidationError::InvalidFieldValue` - For constraint violations
- `ValidationError::InvalidReference` - For missing IDs
- `ValidationError::ConstraintViolation` - For logical inconsistencies
- Context-rich messages with suggestions

### Problem Statement

Invalid inputs currently cause:

1. **Panics during construction** (poor UX)
2. **Cryptic error messages** (e.g., "index out of bounds")
3. **Silent failures** (incorrect results with no warning)
4. **Runtime errors** (crashes after expensive setup)

**Example Issues**:

- `thermal.bus_id = 999` (doesn't exist) → panic during system build
- `edge.probability = 0.5` (probabilities don't sum to 1.0) → silent incorrect policy
- `hydro.min_storage = 200, max_storage = 100` → solver infeasibility
- `recourse.initial_storage = 150` (exceeds max_storage) → numerical issues

### Why This Matters

1. **User Experience**: Clear validation errors prevent confusion
2. **Fail Fast**: Catch errors before expensive SDDP training
3. **Debugging**: Identify root cause immediately, not after 30min training
4. **Production Readiness**: Robust input handling for operational use

### Solution Overview

Implement **4 validation phases** as outlined in `input.rs` TODO comments:

1. **System Validation**: IDs, references, bounds, constraints
2. **Graph Validation**: Node uniqueness, probabilities, basic structure
3. **Recourse Validation**: Storage bounds, distribution parameters
4. **Cross-Validation**: Reference consistency across files

All validations use T3.9's `PowersError` system for clear, actionable error messages.

## Acceptance Criteria

### System Validation

- [ ] **ID Ranges**: Given system entities, when IDs are not sequential from 0, then return `ValidationError::InvalidFieldValue`
- [ ] **Bus References**: Given line/thermal/hydro, when `bus_id` doesn't exist, then return `ValidationError::InvalidReference` listing available bus IDs
- [ ] **Capacity Constraints**: Given line, when `direct_capacity < 0` or `reverse_capacity < 0`, then return `ValidationError::InvalidFieldValue`
- [ ] **Thermal Constraints**: Given thermal, when `min_generation > max_generation`, then return `ValidationError::ConstraintViolation`
- [ ] **Hydro Constraints**: Given hydro, when `min_storage > max_storage` or `min_turbined_flow > max_turbined_flow`, then return `ValidationError::ConstraintViolation`
- [ ] **Hydro Productivity**: Given hydro, when `productivity <= 0`, then return `ValidationError::InvalidFieldValue`
- [ ] **Downstream References**: Given hydro, when `downstream_hydro_id` doesn't exist, then return `ValidationError::InvalidReference`

### Graph Validation

- [ ] **Node ID Uniqueness**: Given nodes, when IDs are not unique, then return `ValidationError::ConstraintViolation`
- [ ] **Stage Ordering**: Given nodes, when stage IDs are not sequential from 0, then return `ValidationError::InvalidFieldValue`
- [ ] **Edge References**: Given edges, when `source_id` or `target_id` doesn't exist, then return `ValidationError::InvalidReference`
- [ ] **Probability Bounds**: Given edge, when `probability <= 0` or `probability > 1`, then return `ValidationError::InvalidFieldValue`
- [ ] **Probability Normalization**: Given outgoing edges from a node, when probabilities don't sum to 1.0 (±1e-6), then return `ValidationError::ConstraintViolation` showing actual sum
- [ ] **Discount Rate**: Given edge, when `discount_rate < 0`, then return `ValidationError::InvalidFieldValue`
- [ ] **Risk Measure**: Given node, when `risk_measure` not in ["expectation", "cvar", "worstcase"], then return `ValidationError::InvalidFieldValue` listing valid options

### Recourse Validation

- [ ] **Initial Storage Length**: Given initial storages, when count doesn't match system hydros, then return `ValidationError::ConstraintViolation`
- [ ] **Storage Bounds**: Given initial storage, when value < min_storage or > max_storage, then return `ValidationError::ConstraintViolation` with bounds
- [ ] **Hydro ID References**: Given initial storage, when `hydro_id` doesn't exist in system, then return `ValidationError::InvalidReference`
- [ ] **Distribution Parameters (LogNormal)**: Given inflow distribution, when `mu <= 0` or `sigma <= 0`, then return `ValidationError::InvalidFieldValue`
- [ ] **Distribution Parameters (Normal)**: Given load distribution, when `sigma <= 0`, then return `ValidationError::InvalidFieldValue`
- [ ] **Scenario Counts**: Given season uncertainty, when `num_branchings = 0`, then return `ValidationError::InvalidFieldValue`

### Cross-Validation

- [ ] **Graph-System Consistency**: Given graph node season_id, when corresponding season not in recourse uncertainties, then return `ValidationError::InvalidReference`
- [ ] **Recourse-System Consistency**: Given recourse load distribution, when `bus_id` doesn't exist in system, then return `ValidationError::InvalidReference`
- [ ] **Recourse-System Consistency**: Given recourse inflow distribution, when `hydro_id` doesn't exist in system, then return `ValidationError::InvalidReference`

### Integration

- [ ] **Validation Checkpoint**: Given `Input::from_paths()`, when loading files, then all validations run before returning
- [ ] **Validation Ordering**: Given validation phases, when running, then system → graph → recourse → consistency (fail fast on dependencies)
- [ ] **Performance**: Given validation, when benchmarking, then overhead < 100μs (<0.02% of typical training time)

  ```rust
  fn validate_probability_sum(
      source_id: usize,
      edges: &[GraphEdgeInput],
  ) -> Result<(), PowersError> {
      let sum: f64 = edges.iter()
          .filter(|e| e.source_id == source_id)
          .map(|e| e.probability)
          .sum();
      if (sum - 1.0).abs() > 1e-6 {
          return Err(PowersError::Validation(Box::new(
              ValidationError::ConstraintViolation { ... }
          )));
      }
      Ok(())
  }
  ```

## Technical Notes

### Implementation Approach

**Validation Order** (fail fast on dependencies):

1. Config (already done in T3.7)
2. System (no dependencies)
3. Graph (no dependencies on system, but system exists)
4. Recourse (depends on system for bounds/references)
5. Consistency (depends on all above)

**Error Messages** (leverage T3.9):

- Use `ValidationError::InvalidFieldValue` for constraint violations
- Use `ValidationError::InvalidReference` for missing IDs (list available IDs)
- Use `ValidationError::ConstraintViolation` for logical inconsistencies (show actual vs expected)
- Include file name (e.g., "system.json"), field name, value, constraint, suggestion

**Edge Cases**:

- Empty arrays: Valid (e.g., `lines: []` for single-bus system)
- Zero values: Context-dependent (0 cost OK, 0 iterations NOT OK)
- Floating-point comparison: Use tolerance (1e-6) for probability sums
- Null values: Handle `downstream_hydro_id: null` (valid terminal hydro)

**Performance Considerations**:

- Use HashSet for uniqueness checks (O(n) instead of O(n²))
- Group validations by entity type (single pass through arrays)
- Early return on first error (fail fast)
- Target: <100μs total validation overhead (<0.02% of typical 5-second training)

**Backward Compatibility**:

- `Input::build()` unchanged (calls `from_paths()` internally)
- Existing valid inputs continue to work
- New validations catch previously silent errors

**Deferred to Future** (explicitly out of scope):

- Topological sort for hydro cascade cycles (complex, rare edge case)
- Graph reachability algorithms (BFS/DFS) for connectivity
- Date/time parsing validation (currently strings, not parsed)
- Performance profiling of validation overhead in production

### Testing Strategy

**Test Structure**:

- **Positive tests**: Valid inputs pass validation
- **Negative tests**: Invalid inputs fail with correct error type
- **Error message tests**: Errors include context, constraint, suggestion
- **Integration tests**: Validation runs in `from_paths()`

**Test Data**:

- Use example files as baseline (known valid)
- Create invalid variants by modifying one field at a time
- Test boundary conditions (e.g., probability = 1.0 vs 1.000001)

**Coverage Target**:

- 68 new tests (20 + 18 + 15 + 10 + 5 integration)
- Each validation rule has positive + negative test
- Each error type has message content test
