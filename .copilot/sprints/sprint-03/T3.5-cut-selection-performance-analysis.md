## Context

Cut selection is a critical hot path in SDDP backward pass. Current implementation uses **Level-1 dominance** (O(n) per cut evaluation), which is known to be efficient. However, performance characteristics under different cut pool sizes and strategies are not well understood.

**Current State**:

- Level-1 dominance implemented (Sprint 2 validation ✅)
- No performance profiling of cut selection
- No comparison to alternative strategies
- No documentation of performance characteristics
- Unknown behavior at scale (10,000+ cuts)

**Need**: Comprehensive performance analysis of cut selection to validate current implementation and identify optimization opportunities.

**Questions to Answer**:

1. How does cut selection time scale with cut pool size?
2. Is Level-1 dominance the fastest strategy for typical use cases?
3. What's the overhead of cut selection vs total backward pass time?
4. Are there optimization opportunities (caching, parallelization)?
5. What are the trade-offs between selection strategies?

**Caching Optimization**:

```rust
// Before: Recompute slope every check
fn check_dominance(cut1: &Cut, cut2: &Cut, state: &[f64]) -> bool {
    let slope1 = cut1.compute_slope(state);  // Expensive
    let slope2 = cut2.compute_slope(state);  // Expensive
    slope1 < slope2
}

// After: Cache slopes
struct CachedCut {
    cut: Cut,
    cached_slope: Option<f64>,
}

fn check_dominance_cached(cut1: &CachedCut, cut2: &CachedCut, state: &[f64]) -> bool {
    let slope1 = cut1.cached_slope.unwrap_or_else(|| cut1.compute_slope(state));
    let slope2 = cut2.cached_slope.unwrap_or_else(|| cut2.compute_slope(state));
    slope1 < slope2
}
```

**Early Termination**:

```rust
// If cut is clearly dominated, stop checking
fn is_dominated(candidate: &Cut, pool: &[Cut], state: &[f64]) -> bool {
    let candidate_slope = candidate.compute_slope(state);

    for existing in pool {
        let existing_slope = existing.compute_slope(state);
        if existing_slope < candidate_slope - EPSILON {
            return true;  // Clearly dominated, stop early
        }
    }
    false
}
```

### Edge Cases

1. **Empty cut pool**: O(1), no filtering needed
2. **Single cut**: O(1), always add
3. **All cuts identical**: Worst case for dominance checking
4. **High-dimensional state**: Slope computation more expensive

### Performance Considerations

- **Slope computation**: Dot product of cut gradient with state (O(d) for d dimensions)
- **Dominance check**: Compare slopes pairwise (O(n) for n cuts)
- **Total complexity**: O(n × d) per backward pass
- **Memory**: O(n) for cut storage

### Alternative Strategies

**Level-2 Dominance**:

- More aggressive: Remove cut if dominated at ANY sampled state
- Pro: Fewer cuts (memory efficient)
- Con: Risk of removing cuts useful at other states

**Parallel Dominance**:

- Check multiple cuts concurrently with Rayon
- Pro: Speedup on large cut pools (>1000 cuts)
- Con: Overhead for small pools

**Lazy Dominance**:

- Defer dominance checking until cut pool exceeds threshold
- Pro: No overhead when few cuts
- Con: Periodic spikes in backward pass time
