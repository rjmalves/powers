## Context

T3.5 discovered and implemented a **batch cut selection architecture** that fixes a critical non-determinism bug in the current SDDP implementation. The batch API is complete and tested, but **not yet integrated** into the SDDP backward pass.

**Current State**:

- ✅ Batch API implemented: `FutureCostFunction::add_cuts_batch()` in `src/fcf.rs`
- ✅ Data structures defined: `CutStatePair`, `CutSelectionResult`
- ✅ 11 unit tests passing (batch correctness, determinism, edge cases)
- ✅ 16 performance benchmarks passing (154× speedup measured!)
- ✅ Comprehensive documentation (design doc, performance analysis)
- ❌ **SDDP still uses per-thread locking** (`src/sddp/mod.rs:1228`)

**Critical Issues with Current Implementation**:

1. **Non-Determinism Bug** (PRODUCTION BLOCKER):

   - Thread finish order determines cut selection results
   - Same problem + same seed → different policies (non-reproducible)
   - Cannot validate, debug, or compare algorithm performance
   - Severity: 🔴 CRITICAL

2. **Lock Contention Performance Bug**:
   - 15-25% CPU time wasted on lock contention (8 cores)
   - Thread efficiency: 42% (current) vs 95% (batch)
   - Cut selection: 216 µs (current) vs 1.4 µs (batch) = **154× slower**
   - Severity: 🟡 HIGH

**Solution**: Integrate the tested batch API into SDDP backward pass to fix both issues.

**Location**: `src/sddp/mod.rs` (around line 1180-1230)

```rust
// CURRENT: Per-thread locking (PROBLEM)
for child_id in past_node_ids {

            Arc::clone(&parent_fcf_node.data),

```

**New Implementation** (PHASE 1-2-3 architecture):

```rust
// PHASE 1: Compute cuts in parallel (NO LOCK)
let cut_state_pairs: Vec<(usize, fcf::CutStatePair)> = past_node_ids
    .par_iter()
    .map(|&child_id| {
        let child_data_node = node_data_graph.get_node(child_id)?;
        let child_subproblem_node = subproblem_graph.get_node(child_id)?;

        let cut_state_pair = child_subproblem_node.data.compute_new_cut(
            &child_data_node.data,
            &child_subproblem_node.data.state.to_coefficients(),
            &child_data_node.data.system,
        );

        Ok((child_id, cut_state_pair))
    })
    .collect::<Result<Vec<_>, String>>()?;

// PHASE 2: Batch cut selection (SINGLE LOCK, deterministic)
let selection_results = {
    let mut fcf = parent_fcf_node.data.lock().unwrap();
    fcf.add_cuts_batch(cut_state_pairs.into_iter().map(|(_, pair)| pair).collect())
};  // Lock released immediately

// PHASE 3: Apply results to models in parallel (NO LOCK)
selection_results
    .par_iter()
    .zip(past_node_ids)
    .try_for_each(|(result, &child_id)| {
        let parent_subproblem = subproblem_graph
            .get_node_mut(parent_id)?
            .data;

        parent_subproblem.apply_cut_selection_result(
            result,
            &parent_fcf_node.data,
        )
    })?;
```

## Technical Notes

### Implementation Approach

**Key Design Decision**: Use 3-phase architecture

1. **Phase 1 (Parallel Compute)**: No shared state

   - Each thread computes its cut independently
   - No locks needed
   - Collects `CutStatePair` objects into vector

2. **Phase 2 (Batch Select)**: Single lock, deterministic

   - Acquire FCF lock once
   - Process all cuts in order (deterministic)
   - Return `CutSelectionResult` for each
   - Release lock immediately

3. **Phase 3 (Parallel Apply)**: Independent operations
   - Each subproblem updates its own solver model
   - Can be parallelized with Rayon
   - Brief FCF locks only to read cut data

**Performance Characteristics**:

- Lock acquisitions: N (threads) → 1 per stage
- Thread waiting time: Eliminated
- Cache locality: Improved (sequential processing)
- Expected speedup: 5-10% total SDDP time

### Edge Cases to Handle

1. **Empty child node list**: No cuts to add
   - Handle gracefully: empty vector → no-op
2. **Single child node**: Batch with single element
   - Still use batch API for consistency
3. **Very large batches**: 1000+ cuts

   - Pre-allocate vectors with capacity
   - Already tested in benchmarks (10,000 cuts)

4. **Solver model doesn't exist**: Some subproblems have no model

   - Check `if let Some(model) = self.model.as_mut()`
   - Skip model operations, still update FCF

5. **Error in Phase 1**: One child fails to compute cut
   - Use `Result` and `?` operator
   - Fail fast: abort backward pass if any child fails

### Thread Safety Considerations

**Shared Resources**:

- `FutureCostFunction`: Protected by `Arc<Mutex<>>` (existing)
- `Subproblem` models: Each thread owns its subproblem (safe)
- `DirectedGraph`: Immutable during backward pass (safe)

**Synchronization Points**:

- After Phase 1: Implicit barrier (`.collect()` waits for all threads)
- Phase 2: Single-threaded (lock held)
- After Phase 2: Lock released before Phase 3
- Phase 3: No synchronization needed (independent operations)

**Race Conditions**: None expected

- Phase 1: No shared mutable state
- Phase 2: Single-threaded
- Phase 3: Each subproblem is independent

**Metrics to Track**:

- Total backward pass time (should decrease 5-10%)
