# T1.1: Set up test infrastructure and fixtures

**Sprint**: 1  
**Estimate**: 5 hours  
**Priority**: Critical  
**Type**: Infrastructure  
**Dependencies**: None

## Description

Establish the foundational test infrastructure for POWE.RS. This includes setting up the test directory structure, creating common fixtures (test data), implementing utility functions for testing, and creating a mock solver implementation that can be used for isolated testing without depending on HiGHS.

## Context

Currently, POWE.RS has minimal testing infrastructure. To build a comprehensive test suite efficiently, we need:

1. Reusable test fixtures (systems, scenarios, problems)
2. Helper functions to reduce boilerplate
3. A mock solver to test algorithm logic independently of HiGHS
4. Clear organization for test files

This foundation will be used by all subsequent testing tickets.

## Acceptance Criteria

- [ ] Test directory structure created and documented
- [ ] At least 3 common test fixtures implemented (trivial, simple, medium systems)
- [ ] Mock solver implementation that satisfies `Solver` trait
- [ ] Test utilities for common operations (e.g., cut comparison, state validation)
- [ ] All fixtures have doc comments explaining their purpose
- [ ] Tests compile and run (even if they're just placeholders)

## Technical Notes

### Mock Solver Design

The mock solver should:

- Implement the `Solver` trait from `src/solver.rs`
- Allow configuration of return values (status, objective, solution)
- Track method calls (build, add_constraint, optimize, etc.)
- Support state to verify correct usage patterns

Example usage:

```rust
let mut mock_solver = MockSolver::new()
    .with_objective_value(42.0)
    .with_solution(vec![1.0, 2.0, 3.0]);

// Use in tests
let result = mock_solver.optimize();
assert_eq!(result.status, SolverStatus::Optimal);
assert_eq!(mock_solver.optimize_call_count(), 1);
```

### Fixture Design Principles

1. **Simplicity**: Start with minimal fixtures that are easy to reason about
2. **Reusability**: Fixtures should be usable across multiple tests
3. **Clarity**: Clear naming and documentation
4. **Consistency**: All fixtures follow same patterns

### Test Organization Philosophy

- `tests/` for integration tests (test the public API)
- Unit tests can live in module files (`#[cfg(test)] mod tests { ... }`)
- Fixtures should be shared across tests
- Each test file tests one module or concept
