### Architecture

**3-Phase Batch Cut Selection**:

```
Phase 1: COMPUTE (Parallel, no FCF lock)
├─ Handler 1 → compute_cut_for_backward_step() → CutStatePair
├─ Handler 2 → compute_cut_for_backward_step() → CutStatePair
├─ Handler 3 → compute_cut_for_backward_step() → CutStatePair
└─ ... → Collect all pairs

Phase 2: SELECT (Serial, single FCF lock, deterministic)
├─ Capture active_cut_ids_before
├─ Lock FCF (ONCE)
├─ fcf.add_cuts_batch(all_pairs) → Vec<CutSelectionResult>
└─ Unlock FCF

Phase 3: APPLY (Parallel, no FCF lock)
├─ Handler 1 → apply_result_to_subproblem(result[0])
├─ Handler 2 → apply_result_to_subproblem(result[1])
├─ Handler 3 → apply_result_to_subproblem(result[2])
└─ ... → Update all solver models independently
```

### Key Technical Insights

1. **Parallelism Pattern**: Multiple handlers process SAME stage in parallel (not children of a stage)
2. **Shared vs Independent State**:
   - Shared: `future_cost_function_graph` (all handlers update same FCF)
   - Independent: Each handler has own `subproblem_graph` and solver models
3. **Row Index Challenge**: Must capture `active_cut_ids_before` to map cut removals correctly
4. **Edge Case**: Inactive cuts in `removing_cut_ids` → skip removal (never in model)

### Lock Contention Eliminated

**Before** (per-handler locking):

```
Handler 1: compute cut → LOCK FCF → select → update → UNLOCK
Handler 2: compute cut → LOCK FCF → select → update → UNLOCK (waits for Handler 1)
Handler 3: compute cut → LOCK FCF → select → update → UNLOCK (waits for 1 & 2)
...
Result: Serial bottleneck, non-deterministic ordering
```

**After** (batch locking):

```
All Handlers: compute cuts in parallel (no lock)
Main Thread: LOCK FCF → batch select all → UNLOCK (deterministic)
All Handlers: apply results in parallel (no lock)

Result: Parallel execution, deterministic ordering
```

## Bug Fixes

### Critical: Non-Determinism in Backward Pass ✅

**Root Cause**:

- Multiple handlers update shared FCF with individual locks
- Thread scheduling is non-deterministic
- First handler to finish changes pool state → subsequent handlers see different state

**Symptoms**:

- Same seed produces different policies on different runs
- Parallel tests occasionally fail
- Convergence metrics inconsistent

**Fix**:

- Batch all cuts with single FCF lock
- Process cuts in deterministic index order
- All cuts see same pool state

**Validation**:

- 10 consecutive runs with same seed → identical results ✅
- All 869 tests pass consistently ✅
