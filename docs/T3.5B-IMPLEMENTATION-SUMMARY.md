- **Purpose**: Synchronize solver model with FCF pool state after batch selection
- **Location**: Lines ~471-544
- **Operations**:
  - Add new cuts to solver model
  - Return inactive cuts to solver model
  - Remove dominated cuts from solver model
- **Key Feature**: Uses `active_cut_ids_before` to correctly map cut IDs to row indices
- **Important**: Does NOT update FCF pool state (already done by `add_cuts_batch()`)

### 3. Refactored Backward Pass (src/sddp/mod.rs)

**Location**: Lines ~1763-1840 (within `train()` method)

**Old Approach** (per-thread locking):

```rust
train_handlers
    .par_iter_mut()
    .map(|handler| {
        handler.backward_step_at_node(...)  // Each locks FCF individually
    })
    .collect::<Result<(), String>>()?;
```

**New Approach** (3-phase batch):

```rust
// Phase 1: Compute cuts in parallel (no FCF lock)
let cut_state_pairs: Vec<CutStatePair> = train_handlers
    .par_iter_mut()
    .map(|handler| handler.compute_cut_for_backward_step(...))
    .collect()?;

// Phase 2: Batch selection (single FCF lock, deterministic)
let active_cut_ids_before = fcf.lock().unwrap().cut_pool.active_cut_ids.clone();
let selection_results = {
    let mut fcf = fcf.lock().unwrap();
    fcf.add_cuts_batch(cut_state_pairs)  // Deterministic ordering
};

// Phase 3: Apply to models in parallel (no FCF lock)
train_handlers
    .par_iter_mut()
    .zip(selection_results.par_iter())
    .map(|(handler, result)| {
        handler.apply_cut_result_to_subproblem(parent_id, result, &active_cut_ids_before, fcf)
    })
    .collect()?;
```

## Technical Architecture

### Non-Determinism Root Cause (FIXED)

**Problem**: Multiple `SddpTrainHandler` instances process the same stage in parallel, all updating the shared `future_cost_function_graph`. Thread scheduling is non-deterministic, so handlers finish at different times:

- Handler A finishes first → locks FCF → adds cut → changes pool state
- Handler B finishes later → locks FCF → sees different pool → selects differently

**Solution**: Batch all cuts together with a single FCF lock. All cuts see the same pool state and are processed in deterministic index order.

### Key Architectural Insight

- **Parallelism**: Across handlers (forward scenarios), NOT across children of a node
- **Shared State**: `future_cost_function_graph` is shared across all handlers
- **Independent State**: Each handler has its own `subproblem_graph` and `realization_graph`
- **Lock Contention**: All handlers compete for the same FCF lock → performance bottleneck

### Row Index Mapping Challenge

**Problem**: After `add_cuts_batch()` updates the FCF pool state, we can't look up old cut positions to find row indices for removal.

**Solution**: Capture `active_cut_ids_before` BEFORE batch selection. Use this snapshot to map cut IDs to row indices when removing cuts from solver models.

**Edge Case**: Cuts in `removing_cut_ids` might not be in the active list (never added to model because pool was at capacity). Solution: Skip removal if cut not found in `active_cut_ids_before`.
